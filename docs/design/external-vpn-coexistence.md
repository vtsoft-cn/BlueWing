# 系统代理模式与官方 VPN 客户端共存

日期：2026-10-27。

## 问题与依据

系统代理模式没有创建 BlueWing TUN 网卡，但旧配置始终开启 `route.auto_detect_interface`。sing-box 会将出站连接绑定到默认网卡，从而跳过 Windows 为其他 VPN 目标选择的专用接口。官方说明见 [auto_detect_interface](https://sing-box.sagernet.org/configuration/route/#auto_detect_interface)。

本机复现时，官方 VPN 已建立专用路由，系统直连内网 HTTPS 返回 HTTP 401（服务器要求认证）；经 BlueWing 时在本机报地址上下文无效。隔离原生核心仅切换该选项，开启时失败，关闭时获得相同 HTTP 401，确认了网络路径差异。测试没有提交账号、密码或验证码。

## 修复

- 没有实际 TUN 入站时关闭默认网卡自动绑定，让 Windows 按目标地址选择本地或官方 VPN 路由。
- TUN 实际启用时保留该选项，继续防止核心流量进入自身 TUN 形成循环。
- 用户选择 TUN、但因普通用户权限回退为系统代理时，同时关闭网卡绑定；保留用户原先保存的 TUN 设置。
- 不修改 Windows 路由、网卡优先级、其他 VPN 配置、公司授权规则、公网节点和密码。

此修复覆盖系统代理模式中的默认网卡误绑定。TUN 与不同官方客户端并行、多个官方 VPN 的重叠网段、其他客户端切换系统默认路由或实施网络访问限制，需分别验证；不能根据一次 HTTPS 连通性测试宣称所有组合均兼容。

## 验证

1. 配置测试覆盖 TUN 关闭、TUN 正常启用、调用方强制关闭 TUN，均经过真实 sing-box 配置校验。
2. 集成测试模拟无管理员权限，用真实核心启动回退配置：不创建 TUN、清除默认网卡绑定、本机 HTTP 可达，保存设置不变。
3. 实机对比系统直连、旧绑定及修复后配置访问同一内网地址；同时验证国内普通公网和国外代理。
4. 不将 HTTP 401 当成业务登录成功；它仅证明 TLS/HTTP 链路已抵达要求认证的服务，页面及业务登录由用户验收。

本次应用测试 134 项、真实核心集成测试 13 项及正式构建通过。当前安装程序尚需更新后重新启动核心，不能把隔离验证成功当作已经修复了运行中的旧进程。

## 应用配置的方式

本次尝试通过兼容 API `PUT /configs` 更新启动选项，但实测未生效，因此未写入用户配置。上游 [configs.go](https://github.com/SagerNet/sing-box/blob/testing/experimental/clashapi/configs.go) 的该处理器只返回成功，不执行整体配置重载。应用应通过自身核心生命周期重启加载新配置，不能以 HTTP 204 判断启动参数已应用。测试期间原有代理及其他 VPN 保持原配置。
